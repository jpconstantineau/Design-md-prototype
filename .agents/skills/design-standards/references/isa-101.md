# ISA-101: operator-centered HMI design

Use for operational dashboards, exception presentation, HMI information hierarchy, or HMI lifecycle artifacts.

## Source and scope

[ISA's current catalog](https://www.isa.org/standards-and-publications/isa-standards/isa-101-standards) lists **ISA-101.01-2015**, *Human Machine Interfaces for Process Automation Systems*, with **ISA-TR101.01-2022**, *HMI Philosophy*, and **ISA-TR101.02-2019**, *HMI Usability and Performance*. Its scope is industrial process-automation HMIs and their lifecycle, not a universal web styling standard. Public sources checked 2026-11-15.

The guidance below is an original practical application of public implementation material. Its headings are review topics, not an exhaustive or verbatim list of ISA clauses. The full licensed standard was not reviewed here; verify mandatory requirements against the applicable edition and qualified domain review. A web dashboard, muted palette, or DESIGN.md file does not establish ISA conformance. Web examples below are hypothetical cross-domain analogies.

## Operator-task-driven workflows

- **Apply:** identify what the operator must notice, decide, do, and confirm in normal and abnormal situations. Build the display around those tasks and the operator's actual area of responsibility. Use a P&ID or equipment schematic when it helps a specific task, rather than copying its geography as the whole interface.
- **Example:** a proposed indexing view groups queue progress, a failed worker, the reason, and permitted recovery actions around diagnosing a stalled run; raw service topology is available for deeper diagnosis.
- **Check:** have a representative user detect a problem, explain its effect, choose an action, and verify the result without reconstructing the workflow from unrelated screens.

[Yokogawa's task-analysis guidance](https://www.yokogawa.com/ca/library/resources/media-publications/isa-101-toward-a-more-effective-hmi-strategy/) supports task-led displays. Its 2015 article predates final publication, so it is implementation context, not proof of final normative wording. [Hollifield's high-performance HMI guidance](https://www-prod.isa.org/web/acom/article/the-high-performance-hmi) also allows useful equipment detail; a blanket ban on schematics would misapply the idea.

## Restrained visuals and non-color state cues

- **Apply:** use neutral or muted normal surfaces and deliberate emphasis for meaningful exceptions. Preserve the project's brand where it remains useful and accessible. Pair status color with readable words, shapes, or symbols; keep controls, selected states, text, and focus perceptible. Remove decorative 3D effects that compete with the task.
- **Example:** ordinary queue rows remain readable without bright status fills. A blocked row says **Blocked**, explains the restriction, and includes a distinct symbol; selection and keyboard focus remain distinguishable from failure.
- **Check:** inspect normal, selected, blocked, and error states without relying on hue. Run the relevant [WCAG checks](wcag-22.md), including actual contrast and keyboard focus, rather than treating grayscale as evidence of accessibility.

[ISA's DCS migration article](https://www.isa.org/intech-home/2023/april-2023/features/how-dcs-migration-improves-operator-experience) describes sparse color as one part of a broader task-and-information redesign. [Hollifield](https://www-prod.isa.org/web/acom/article/the-high-performance-hmi) supports redundant state coding. The web palette and WCAG safeguards here are local applications, not universal ISA color tokens.

## Four-level information hierarchy

Use this suggested display model to separate scope and detail. [ISA's operator-performance article](https://www.isa.org/intech-home/2023/2023-february-2023/features/four-pillars-operator-performance) calls the hierarchy suggested; [Graham Nasby's public technical presentation, page 36](https://www.grahamnasby.com/files_publications/NasbyG_2017_HighPerformanceHMIs_IntelligentWastewaterSeminar_WEAO_sept14-2017_slides-public.pdf#page=36) supplies the following level descriptions in more detail.

| Level | Industrial purpose | Optional web translation |
| --- | --- | --- |
| **1. System overview** | Broad condition of the operator's span of responsibility, including important exceptions. This need not be the entire plant. | Workspace or service overview. |
| **2. Sub-process** | A unit, process area, or major operational task and its working controls. | A subsystem or workflow view. |
| **3. Equipment details** | Detailed equipment, process, or control information needed for focused work. | One worker, job, or resource. |
| **4. Task / diagnostics** | Specialized diagnostic, procedural, or configuration detail. | Logs, diagnostic evidence, or a focused configuration task. |

- **Apply:** select the views the task needs. These are information levels, not a compulsory four-click navigation path or fixed widget allocation. Place a faceplate or control where its task requires it; retain access to the broader context.
- **Example:** a future indexing overview links directly to the affected worker and its diagnostic detail while retaining the selected workspace. A simple product may combine views instead of manufacturing four screens.
- **Check:** locate an exception from the overview, reach the necessary control or evidence, and return without losing the selected scope. Explain what question each view answers.

[Rockwell's technical paper, page 7](https://literature.rockwellautomation.com/idc/groups/literature/documents/wp/proces-wp016_-en-p.pdf#page=7) explicitly distinguishes display levels from navigation depth. Public descriptions vary in where particular controls appear; the table is a usable model, not an exclusive placement rule.

## Streamlined contextual navigation

- **Apply:** keep task-critical information, controls, and action feedback together. Provide predictable overview, related-detail, and return routes with visible scope. Prefer direct contextual access over repeated menu searches; use a dialog only when it helps the task and preserves context. Optimize successful task completion, not an arbitrary click count.
- **Example:** a blocked permission shows its reason beside the control and links to the relevant policy. Returning retains the same selected agent rather than resetting the list.
- **Check:** walk the task with keyboard input and confirm the user can identify their location, inspect the reason, act when permitted, and see the outcome without an unnecessary chain of pop-ups.

[ISA's operator-performance article](https://www.isa.org/intech-home/2023/2023-february-2023/features/four-pillars-operator-performance) supports placing action and response together. Use the [ISO interaction principles](iso-9241-110.md#the-seven-interaction-principles) for the broader predictability and recovery review.

## Relevant, prioritized alarms and in-context trends

**Separate alarm management from display design.** [ISA-18.2-2016](https://www.isa.org/standards-and-publications/isa-standards/isa-18-series-of-standards), *Management of Alarm Systems for the Process Industries*, addresses the industrial alarm lifecycle. Rationalization establishes whether an alarm is justified, its consequences, response, and priority; it is not merely reducing the visible count. See [Dunn and Sands' ISA explanation](https://www.isa.org/intech-home/2020/march-april/features/alarm-management-questions-that-everyone-asks).

- **Apply:** distinguish actionable exceptions from ordinary status. Show priority, affected object, condition, and useful response context. Industrial priorities, thresholds, suppression, and escalation require the site's alarm philosophy and qualified process engineering. In a web adaptation, keep active critical items discoverable and make filtering or grouping explicit; an aesthetic alarm cap is not a safety strategy.
- **Example:** a hypothetical failed run states what is blocked and the available next step. Add recent throughput and queue history if their trajectory helps diagnosis; a simple access-denied message may need a policy explanation rather than a chart.
- **Check:** exercise simultaneous low- and high-priority exceptions and active filters. Verify that urgent items remain discoverable and their response is clear. Where a trend is used, check its time window, scale, source, and relation to the decision using the [evidence guidance](edward-tufte-evidence.md).

Contextual trends are one useful technique in [Hollifield's HMI examples](https://www-prod.isa.org/web/acom/article/the-high-performance-hmi), not a requirement to attach a sparkline to every alert. The UI review above does not replace industrial alarm rationalization or establish ISA-18.2 conformance.

## Lifecycle artifacts: philosophy, style guide, toolkit

[Rockwell's public lifecycle explanation, page 5](https://literature.rockwellautomation.com/idc/groups/literature/documents/wp/proces-wp016_-en-p.pdf#page=5) and [Yokogawa's implementation guidance](https://www.yokogawa.com/ca/library/resources/media-publications/isa-101-toward-a-more-effective-hmi-strategy/) distinguish these three artifacts. The roles and web mappings below are proposed ways to apply that distinction, not ISA-assigned job titles or a claim that these files alone satisfy the standard.

### HMI philosophy: goals, principles, and responsibility

- **Apply:** have the site or product owner work with operators, engineering, and design to define the intended tasks, design principles, responsibilities, and change/review process. Keep this foundation independent of a particular component library.
- **Example:** a web product's design principles define clear effective state, visible action outcomes, and who approves changes to those behaviors.
- **Check:** trace a proposed interface decision to a user need and an accountable owner. Verify that stakeholders agree on the intended outcome before choosing widgets.

### HMI style guide: concrete rules for the chosen platform

- **Apply:** have design-system owners translate the philosophy into platform-specific layouts, navigation, typography, color roles, states, and interaction examples. For a web product, [DESIGN.md](design-md.md) can carry tokens and prose rules as part of this guide; supplement it with behavior examples where needed.
- **Example:** the guide defines the selected-object region and how immediate changes, pending requests, and confirmed outcomes appear in the existing design system.
- **Check:** compare two representative screens against the same rules. Resolve contradictory prose, tokens, and examples before implementation.

### HMI toolkit: reusable, tested implementation

- **Apply:** have implementation owners supply reusable symbols, controls, templates, and behavior that implement the guide. The web analogue is the project's shared components and tests, using its chosen stack rather than introducing a new framework by default.
- **Example:** a shared status component combines text, symbol, and semantic color; its tests cover loading, failure, keyboard use, and supported themes.
- **Check:** verify reuse and test the actual rendered states. A pre-tested component still needs integration and workflow testing in its deployment context.

Keep the three artifacts aligned through design, implementation, operation, and reviewed changes. Record owners, revisions, observed task results, and unresolved findings in the [review record](review-checklist.md). For a real industrial deployment, obtain the licensed requirements, domain validation, and operator training appropriate to the site.
