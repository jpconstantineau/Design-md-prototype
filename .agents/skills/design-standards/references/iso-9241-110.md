# ISO 9241-110: interaction

Use for task flow, control behavior, feedback, correction, and learning.

## The seven interaction principles

This is the complete principle-heading set in **ISO 9241-110:2020** order, clauses 5.1-5.7, verified in the [ANSI-authorized preview, contents page iii (PDF page 3)](https://webstore.ansi.org/preview-pages/ISO/preview_ISO%2B9241-110-2020.pdf#page=3). Each clause's `.1` subsection contains the principle statement; its later subsections contain recommendations, not additional principles.

Only the short headings below are ISO wording. **Apply**, **Example**, and **Check** are this playbook's original operational interpretation, not ISO definitions, clause text, or a conformance assessment. Examples are illustrative product scenarios, not claims about an existing implementation.

### 5.1 Suitability for the user’s tasks

- **Apply:** organize the workflow around the user's intended outcome, remove unnecessary steps, and place frequent actions near their target.
- **Example:** an access editor starts with the agent and folders being configured, then presents the relevant permissions together rather than scattering them across decorative cards.
- **Check:** ask a representative user to complete the main task; record any unnecessary navigation, repeated input, or irrelevant controls encountered.

### 5.2 Self-descriptiveness

- **Apply:** make available actions, their effects, and the system's current processing state understandable where the user needs them.
- **Example:** an immediate-apply toggle says that changes take effect immediately, shows pending work during the request, and confirms application only after success. A staged editor instead marks its draft as unsaved.
- **Check:** before and after an action, ask the user to explain what it does and whether the result is pending, effective, or failed without outside coaching.

### 5.3 Conformity with user expectations

- **Apply:** follow familiar domain and platform conventions and keep equivalent actions and responses consistent across the product.
- **Example:** selecting a navigation destination changes the page; selecting an object changes the editor's scope. Neither silently applies a permission change.
- **Check:** have the user predict the outcome before activating repeated controls on different screens; investigate mismatches between expectation and behavior.

### 5.4 Learnability

- **Apply:** help people discover unfamiliar actions, understand their consequences, and reuse what they learned without repeated instruction.
- **Example:** a short inline explanation defines inherited access beside the first relevant setting, with an optional detail view that remains available on later visits.
- **Check:** observe a first-time task and a repeat attempt; record where help was needed and whether the user can subsequently perform the task without coaching.

### 5.5 Controllability

- **Apply:** let users direct the interaction, choose an appropriate pace or route, and interrupt or revise actions where doing so is safe.
- **Example:** a long-running folder scan exposes a clear Cancel action; a staged editor supports discarding a draft. An immediate-change control instead needs a suitable way to revise or reverse its result.
- **Check:** test interruption and recovery at meaningful points and confirm that the user understands what stopped, what already changed, and what can be done next.

### 5.6 Use error robustness

- **Apply:** prevent foreseeable mistakes, contain their consequences, and support correction while retaining valid work.
- **Example:** a failed permission update identifies the blocked folder and cause, keeps the remaining valid selections, and offers a useful retry or correction path.
- **Check:** deliberately trigger an invalid input and a rejected operation; verify that the explanation, retained data, and recovery path allow completion without starting over.

### 5.7 User engagement

- **Apply:** support confidence and worthwhile progress through truthful feedback, useful outcomes, and appropriate opportunities for user involvement.
- **Example:** after a confirmed change, summarize the effective access and offer a relevant next action; avoid false success messages or pressure to continue unrelated work.
- **Check:** ask whether the user trusts the result and understands the value and next step; compare their explanation with the actual system state.

## Source and scope

[ISO 9241-110:2020](https://www.iso.org/standard/75258.html), edition 2, was published in May 2020 and remains current after confirmation in 2025. Its scope addresses interaction rather than aesthetics or corporate identity. Sources and heading order verified 2026-11-15.

Use the 2020 set above rather than an older dialogue-principles list. Individualization is included within controllability in this edition, not an eighth principle. The licensed standard is needed for the actual principle statements, recommendations, and clause-level evaluation.

## Review evidence

For every principle, record the relevant scenario, observation, and result: pass, fail, not tested, or not applicable with a reason. Include the actual change contract, whether immediate or staged, and a blocked/error/recovery path. A complete heading list and completed local checks do not establish ISO conformance.

Use [ISO 9241-112's presentation principles](iso-9241-112.md#the-six-presentation-principles) for information-presentation failures and [WCAG](wcag-22.md) for accessibility criteria.
